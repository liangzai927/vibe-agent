# 个人 agent：24 小时待机 + 事件监听

> 目标：它一直在跑，到点自己醒来，该提醒的提醒、该干的干。
>
> **本文只做设计，不含实现。**

---

## 一、现在缺什么

| | 现在 | 需要 |
|---|---|---|
| **常驻** | `va web` 前台跑，关终端就没了 | 后台跑 + 崩溃自拉起 + 开机自启 |
| **自己醒来** | 只在你发消息时动 | 调度器：到点主动触发 |
| **告诉你** | 只有界面 | 系统通知 / webhook（界面没开也能收到） |

---

## 二、架构：调度器活在 `va web` 里

**不另起一个进程。**

理由：它要用的东西全在 web 进程里——会话运行时、任务对象、事件总线、
审批门、测试门禁、autonomy 设置。另起一个进程等于把这些**全部重建一遍**，
还要处理两者之间的同步（谁在跑、状态在哪、锁怎么加）。

```
va web（常驻）
  ├─ HTTP / SSE 服务          界面、审批、事件推送
  ├─ 会话运行时                每个会话一个 Agent
  ├─ 调度线程 ── 每 30 秒检查一次
  │     └─ 到点了 → 变成一条「用户消息」投进会话
  │                  （走完全一样的流程：任务对象、门禁、审批）
  └─ 监听器 ── 文件 / git / HTTP
```

### 这个设计带来一个很重要的性质

**提醒和任务没有区别。**

```
「3 点提醒我喝水」        → 到点了发通知，完事
「明早把这个 PRD 实现掉」  → 到点了往会话里投一条消息
                            → 正常走工作流、正常过门禁、正常要你审批
```

不需要为「自动任务」再造一套流程——**它就是你发了一条消息，只不过
发消息的是闹钟**。这样 autonomy、任务看板、干预率统计全都自动适用。

## 三、数据模型

```yaml
# <数据根>/schedule.json    运行状态，不进项目（沿用已定的原则）
- id: s-7f3a
  what: "提醒我交 PRD"
  at: "2026-10-20T15:00:00"        # 算好的下一次触发时间
  repeat: null                      # null | daily | weekly:mon | monthly:1
  kind: remind                      # remind 只通知 | task 投消息进会话
  workspace: ""                     # 留空 = 与项目无关（全局提醒）
  session: ""                       # kind=task 时投给哪个会话
  prompt: ""                        # kind=task 时投什么话
  notify: []                        # 留空 = 用默认渠道
  enabled: true
  last_fired: 0
  fired_count: 0
  fail_count: 0                     # 连续失败次数，用来「停下来别刷屏」
```

**存在数据根**——提醒是 agent 的运行状态，不是团队约定。
（和任务状态、事故日志一个道理，见「只把约定放项目里」那一节。）

### 时间表达式

**支持四种，够用了：**

| 写法 | 例子 |
|---|---|
| 绝对 | `2026-10-20 15:00` |
| 相对 | `3天后`、`2小时后`、`下周一` |
| 每天/每周/每月 | `每天 09:00`、`每周一 09:00`、`每月1号 09:00` |
| cron（逃生舱） | `cron:0 9 * * 1-5` |

**为什么不做成只支持 cron**：cron 强大但对人极不友好，
`0 9 * * 1-5` 得查着写。日常的「每天九点」「下周一」用自然说法更好。
真需要复杂表达式的，`cron:` 前缀能直接用。

## 四、通知层

三个渠道，**都失败也不能影响调度**（和提测那边一个原则：
通知失败不是任务失败）。

```
                    ┌─ 界面（事件总线 → SSE → 弹出来）
到点了 ──▶ Notifier ├─ 系统通知（macOS / Windows / Linux）
                    └─ webhook（企业微信 / 钉钉 / 飞书）
```

**界面**：走现成的事件总线，`va web` 开着就能看到。

**系统通知**：
| 平台 | 怎么做 |
|---|---|
| macOS | `osascript -e 'display notification ...'` |
| Windows | PowerShell 的 Toast（**注意：和文件夹选择框一样，参数要走环境变量**，别塞命令行） |
| Linux | `notify-send` |

**webhook**：兼容企业微信 / 钉钉 / 飞书的 JSON 格式（它们的字段略有不同，
用模板区分）。地址从环境变量读——**和 MCP、提测通知一样，不写进配置文件**。

```yaml
# workflow.yaml
notify:
  channels: [ui, system]          # 默认用哪些
  webhook_env: VA_NOTIFY_WEBHOOK  # 地址从哪个环境变量读，留空 = 不用
  webhook_kind: wecom             # wecom | dingtalk | feishu | raw
  quiet_hours: "23:00-07:00"      # 静默时段，这期间只记不弹
  urgent_bypass: true             # urgent=true 的能不能穿透静默时段
```

## 五、四个阶段

### 阶段 1：调度器 + 提醒（地基）

**交付物**

```
schedule(when="2026-10-20 15:00", what="提醒我交 PRD")
schedule(when="每周一 09:00", what="汇总上周提交", kind="task", session="...")
list_schedule()                    # 看有哪些
cancel_schedule(id)                # 取消
```

- 持久化，重启不丢
- 调度线程每 30 秒扫一次
- 到点 → 通知 / 投消息
- 界面能看到（顶栏加个「⏰」入口）

**验收**

- [ ] 设一个 1 分钟后的提醒，到点真的弹出来
- [ ] 重启 `va web`，提醒还在
- [ ] 重复提醒（每天 9:00）会算出下一次
- [ ] **错过会补**：电脑睡了两小时醒来，提醒会说明「本该在 X 提醒」
- [ ] 同一个提醒**不会重复触发**（重入保护）
- [ ] 通知发不出去，调度照常（不影响下一次）

### 阶段 2：常驻

**交付物**

```bash
va daemon start      # 后台跑（写 pid 文件）
va daemon stop
va daemon status     # 在跑吗、跑了多久、最近触发过什么
va daemon logs       # 看日志
va daemon install    # 开机自启（分平台）
va daemon uninstall
```

| 平台 | 开机自启 |
|---|---|
| macOS | `launchd` plist → `~/Library/LaunchAgents/` |
| **Windows** | `schtasks /create /sc onlogon` |
| Linux | systemd user unit |

**崩溃自拉起**：launchd / systemd 都自带（`KeepAlive` / `Restart=always`）。
Windows 的计划任务没有，需要一个看门狗或者接受「崩了就崩了」。

**验收**

- [ ] `va daemon start` 之后关掉终端，它还在跑
- [ ] 重启电脑，它自己起来
- [ ] `va daemon status` 能看到运行时长和最近的触发明细
- [ ] 杀掉进程，launchd/systemd 会把它拉起来

### 阶段 3：事件监听

**交付物**

```yaml
watch:
  - kind: file
    path: docs/prd/*.md
    on: created              # created | changed | deleted
    what: "有新的 PRD，看一眼要不要建任务"
  - kind: git
    repo: ~/work/myproject
    branch: main
    on: new_commits
  - kind: http
    url: http://localhost:8000/health
    expect: 200
    on: down                 # 从通到不通时触发
```

- **文件**：轮询 mtime（简单可靠，不引入 watchdog 依赖），间隔可配
- **git**：定时 `fetch` 后比较
- **HTTP**：定时探测，**只在状态变化时触发**（不是每次都响）

**验收**

- [ ] 往 `docs/prd/` 丢一个文件，它注意到了
- [ ] 同一个文件改两次，触发两次（不是一次）
- [ ] HTTP 探测挂了又恢复，只在「挂」和「恢复」各响一次
- [ ] 监听器本身出错不影响别的监听器

### 阶段 4：让它自己动手

到点不只是提醒，而是「跑一个任务」——**阶段 1 的 `kind: task` 已经做了一半**。

剩下的关键是**边界**（下一节）。

---

## 六、边界：一个会自己醒来的 agent

**这是整个方案里最需要想清楚的部分。**

### 它能做什么

| 动作 | 边界 |
|---|---|
| 发通知 | 随时。无风险 |
| 往会话里投一条消息（相当于你说了句话） | 随时。那条消息走**正常流程** |
| 改代码 / 提交 / 推送 | **要过 autonomy**。默认人工审核——它醒了会问你 |

**关键**：不需要为「自动」单独设计一套权限。**投一条消息进会话**，
后面的事全由现有机制管：任务对象、测试门禁、约定校验、
`autonomy.confirm_before`（提交和提测永远要你点头）。

### 三条硬规则

**① 静默时段**

半夜三点弹通知没人喜欢。`quiet_hours` 期间只记不弹，
第二天早上汇总成一条。

**② 失控保护**

同一个提醒**连续失败 N 次就停下来**，并告诉你「这条一直在失败」。
不这样做的话，一个坏掉的提醒会每 30 秒刷你一次，直到你把整个功能关掉。

**③ 有记录**

它什么时候醒过、做了什么、结果如何——**全部进任务看板**。

一个你不知道它干了什么的个人 agent，比没有还糟。

### 一个要你拍板的问题

**「到点了，但你在忙」怎么办？**

- **A. 排队**：等当前任务跑完再投（安全，但可能延迟很久）
- **B. 丢掉并记一笔**：过时不候（干脆，但可能漏事）
- **C. 只发通知，不动手**：`kind=task` 降级成 `kind=remind`

我倾向 **A + 超时降级到 C**：等一会儿，等不到就只提醒你「本来要做 X」。
**因为一个会插队打断你正在做的事的 agent，很快就会被关掉。**

## 七、和现有东西的关系

| 现有 | 怎么用上 |
|---|---|
| **事件总线** | 通知走它推到界面，不用新写一套推送 |
| **会话运行时** | `kind=task` 就是 `app.submit(...)`，不新写执行路径 |
| **任务看板** | 触发明细显示在这儿——「它什么时候醒过」 |
| **autonomy** | 自己动手要过审，默认人工 |
| **测试门禁** | 自动跑的任务一样要过——**自动不等于免检** |
| **workflow.yaml** | 通知渠道、静默时段、监听项都进配置 |
| **`va update`** | 常驻进程也得能更新——`va update` 要考虑「更新完重启 daemon」 |

---

## 八、要你拍板的几个点

| | 问题 | 我的建议 |
|---|---|---|
| **D1** | 「到点了但你在忙」怎么办 | 排队 + 超时降级成只提醒（见上） |
| **D2** | 错过太久（比如关机一周）的提醒 | 超过 1 天的汇总成一条，别逐条刷 |
| **D3** | 开机自启要不要默认装 | **不默认**。`va daemon install` 显式装 |
| **D4** | Windows 的崩溃自拉起 | 第一版接受「崩了就崩了」，用 `va daemon status` 能看出来 |
| **D5** | 提醒能不能删/改 | 能。界面上直接操作，别只能通过对话 |

---

## 九、建议的顺序

```
阶段 1（调度器 + 提醒）  ← 地基建好，后面全长在它上面
    ↓
阶段 2（常驻）           ← 让它真的 24 小时在
    ↓
阶段 3（事件监听）        ← 从「定时」扩展到「有变化就动」
    ↓
阶段 4（自己动手）        ← 其实阶段 1 的 kind=task 已经做了一半
```

**阶段 1 值得单独做完再做别的**——它是地基，而且做完立刻就能用
（「每天九点提醒我看一眼 PRD」）。
