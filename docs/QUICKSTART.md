# 怎么开始

**一句话**：先跑一条最短的链路，再一步一步加。

> 这跟新同事入职一样——第一次要交代清楚，跑几轮之后就顺了。
> **别一上来就跑一个完整的大功能**，那会同时暴露十个问题，你不知道先修哪个。

---

## 第 0 步：确认环境

```bash
cd vibe-agent

# 有 API key 吗（.env 里）
grep VA_API_KEY .env

# 环境自检
python3 run.py doctor
```

`doctor` 会检查：Python 版本、依赖、git、浏览器、API 连通性。
**有红的先修掉**，后面的事都建在它上面。

---

## 第 1 步：起界面

```bash
python3 run.py web -C ~/你的项目目录
```

浏览器打开提示的地址。你会看到：

- 左边：工作区 + 会话列表
- 中间：对话
- 顶栏：`▤ 任务`（看板）、`⚙ 设置`

---

## 第 2 步：配工作流（第一次只配三样）

```bash
cd ~/你的项目目录
python3 ~/vibe-agent/run.py workflow --init
```

会生成 `.vibe/workflow.yaml`，**里面字段全是注释**，取消哪条哪条生效。

**第一次只取消这三条**，别的先不管：

```yaml
branch:
  # 从哪个分支切出
  base: main                    ← 改成你们实际的分支

test:
  # 逻辑测试命令
  logic: npm run test:unit      ← 有测试才配

submit:
  # 提测推到哪个分支
  target_branch: test           ← **要提测才配；不配就不提测**
```

校验一下：

```bash
python3 ~/vibe-agent/run.py workflow --check
```

**没配的项不会报错，也不会执行**——整个设计就是这样，你配多少它做多少。

---

## 第 3 步：接设计稿（可选，但你会想用）

`.vibe/workflow.yaml` 加：

```yaml
mcp:
  approve: read          # 读工具免问，写工具（改画布）要问
  servers:
    mastergo:
      command: npx
      args: ["-y", "@mastergo/vibe-mcp@latest", "--url=http://localhost:30678"]
      timeout: 120
```

**重启 `va web`**（配置在启动时读）。然后：

1. 打开 MasterGo 客户端，打开设计稿
2. **在设置面板里点「测试连接」** ← 验证链路
3. 连上了会列出工具名

连不上就把界面显示的日志发出来——那里有服务端的 stderr。

---

## 第 4 步：第一次跑 —— **从小的开始**

不要跑一个完整功能。建议先挑一个**半小时能做完的小改动**：
改个文案、加个小筛选、调个样式。

**第一句话可以这么对 agent 说**：

> 实现一个小的改动：`<描述>`。
> 请按工作流走：建分支 → 实现 → 提交。**测试和提测先不用**。

或者带设计稿：

> 按我在 MasterGo 里选中的图层改一下这个页面的样式。
> 请按工作流走。

**然后盯着看**，特别是这几处：

| 看什么 | 在哪看 |
|---|---|
| 它有没有真的建分支、名字对不对 | 对话里，或者 `git branch` |
| commit message 合不合规范 | 对话里 |
| 任务走到哪一步了 | 顶栏 `▤ 任务` |
| 有没有卡住 | 看板上的「在等什么」 |

---

## 第 5 步：跑完**一定要看诊断**

这是最容易被跳过、但最值钱的一步：

> 对 agent 说：**跑一下 diagnose_workflow，看看工作流本身有什么问题。**

或者直接在对话里问「流程哪里不对」。

第一次跑**一定会**暴露几处配置和实际不符，比如：

```
· branch.base 配的是 main，但这个分支不存在
· test.logic 引用的 npm run test:unit 不在 package.json 里
· mock.dir（src/mocks）不存在
· 「联调」这一步 8/10 次被干预（80%）
```

**看到信号之后**：

- 明显的配置错误 → 直接让它改（它会给你 diff 确认）
- 需要你判断的 → 告诉它你希望是什么样

```
你：mock 别放 src/mocks，我们用 src/__mocks__

它：.vibe/workflow.yaml
    @@ -0,0 +1,2 @@
    +mock:
    +  dir: src/__mocks__

    [同意] [拒绝]
```

**这就是「自我进化」的实际样子**——你把判断告诉它一次，它记进配置，
以后不用再说。

---

## 第 6 步：一轮一轮加

**不要一次配全**。按这个顺序加，每加一样跑一轮：

| 轮次 | 加什么 | 你会看到 |
|---|---|---|
| 第 1 轮 | 只配 `branch.base` | 建分支、写代码、提交 |
| 第 2 轮 | 加 `test.logic` + `test.gate: strict` | **测试没过就提交不了** |
| 第 3 轮 | 加 `test.start` + `test.e2e_base_url` | 能跑功能测试 |
| 第 4 轮 | 加 `test.visual_designs` | 样式还原比对 |
| 第 5 轮 | 加 `submit.target_branch` | 提测推送 |
| 第 6 轮 | 加 MasterGo MCP | 直接从设计稿写样式 |

每加一样，**先看它有没有按你预期工作**，再加下一样。

---

## 第 7 步：等它挣到自主权

**默认是人工审核**——每一步推进都要你放行（界面上会问你）。

跑到一定量之后，看板底部会显示：

```
推进模式：人工审核
最近 7 天：19/20 次推进无干预（95%，门槛 95%）
期间没有严重事故
→ **可以开自动推进了**
```

那时候再改成 `autonomy.mode: auto`。**即使开了自动，提交和提测仍然要你点头**
（`autonomy.confirm_before`）——推错了收不回来。

## 常见问题

**Q：它会往我的项目里写东西吗？**

`@` 引用的文件、改的代码、`.vibe/` 下的配置和任务状态——都在项目里，
**这些进 git 是好事**（团队共享约定）。会话记录和记忆在 `VA_DATA_REMOTE`
指向的仓库里，不在项目里。

建议 `.gitignore` 加：

```
.mastergo/          # MasterGo 自己会往这写
```

**Q：跑一半发现配置错了怎么办？**

改了配置**下次会话生效**（当前会话用的还是启动时读的那份）。
重启 `va web` 最快。

**Q：它会不会把没测过的代码提交上去？**

不会——测试门禁拦在 `git_commit` 里面。除非你显式 `override_gate`，
那样会**记一笔严重事故并写进 commit message**，事后查得到。

**Q：我不想要某个行为，怎么关掉？**

大部分都有开关：

```yaml
test:
  gate: off                 # 关掉测试门禁
  visual_stabilize: false   # 关掉截图稳定化
mcp:
  approve: none             # MCP 免审批
autonomy:
  mode: manual              # 人工审核（默认）
```

**没配的东西不会报错也不会执行**，所以直接删掉某一项也是关掉它。

**Q：怎么知道它做的事对不对？**

三处：
1. **看板**（`▤ 任务`）——走到哪了、在等什么
2. **它的 diff**——改文件前会给你看
3. **诊断**——定期跑一次，看有没有信号

---

## 一句话总结

```
配三样 → 跑个小改动 → 看诊断 → 按诊断改配置 → 加下一样 → 重复
```

跑顺几轮之后，它就不太需要你交代了。
