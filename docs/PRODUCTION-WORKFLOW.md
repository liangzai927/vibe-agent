# 生产工作流开发计划

> 目标：让 agent 从「会写代码」变成「能交付」。
>
> 输入一份 PRD，它自己建分支、写代码、mock 后端、跑测试、提交、提测，
> 并且能根据你每次提的优化改进它自己的工作流。
>
> **本文只做设计，不含实现。**

# 第一部分：目标流程

## 全景

```
                 ┌─────────────────────────────────────────────┐
                 │  工作流定义（可读写、可 diff、可 review）      │
                 │  .vibe/workflow.yaml                        │
                 └──────────────────┬──────────────────────────┘
                                    │ 每一步都按它执行
                                    ▼
 ┌────────┐   ┌────────┐   ┌────────┐   ┌────────┐   ┌────────┐
 │ 1 读需求│──▶│ 2 建分支│──▶│ 3 计划 │──▶│ 4 实现 │──▶│ 5 挂起 │
 └────────┘   └────────┘   └────────┘   └────────┘   └───┬────┘
                                                          │ 后端就绪
                                                          ▼
 ┌────────┐   ┌────────┐   ┌────────┐   ┌────────┐   ┌────────┐
 │10 反馈 │◀──│ 9 提测 │◀──│ 8 提交 │◀──│ 7 测试 │◀──│ 6 联调 │
 └───┬────┘   └────────┘   └────────┘   └────────┘   └────────┘
     │                                        ▲
     │                                        │ 门禁：不绿不提交
     └──────────▶ 改进工作流定义 ──────────────┘
```

## 一个具体例子

```
你：实现「订单列表支持按状态筛选」，需求见 docs/PRD-2024-0312.md

agent：
  ✓ 读了 PRD，提取出 4 条验收标准、需要 2 个后端接口
  ✓ 建分支 feature/ORD-312-order-status-filter（从 test 切出）
  ✓ 拆成 6 步计划，其中 3 步标记「依赖后端」
  ✓ 写了 5 个文件，2 个接口先用 mock（按 src/mocks/ 的既有约定）
  ✓ 自测：render_page 渲染不报错
  ⏸ 挂起：等 GET /api/orders?status= 和 POST /api/orders/batch

  …两天后…

你：后端好了，继续

agent：
  ✓ 探测到接口可用，对比 mock 与真实响应 —— 发现真实响应少一个 total 字段
  ✓ 修了前端对这个字段的依赖
  ✓ 启动项目（端口就绪探测通过）
  ✓ 逻辑测试 42 项通过
  ✓ 功能测试：筛选、分页、空态 —— 6 条通过
  ✓ 样式还原：与设计稿差异 0.3%（阈值 1%）
  ✓ 提交：feat(order): 列表支持按状态筛选 (#ORD-312)
  ✓ 推送到 test，CI 通过
  ✓ 提测通知已发

  ⚠ 这次发现 mocks 目录约定和 workflow.yaml 里写的不一致，已提议修正
```

# 第二部分：逐环节拆解

每一步都定义：**输入 / 动作 / 输出 / 门禁 / 失败怎么办**。

门禁是**确定性的**——不是「让模型自己觉得过了」。

---

## 1. 读需求

| | |
|---|---|
| **输入** | PRD 文档路径 / 一段需求描述 / 工单号 |
| **动作** | 读文档 → 提取结构化需求 |
| **输出** | 需求对象（持久化到会话 + 项目） |
| **门禁** | 必须能提取出**可验证的验收标准** |
| **失败** | 验收标准缺失 → **停下来问人**，不许自己编 |

需求对象长这样：

```yaml
id: ORD-312
title: 订单列表支持按状态筛选
source: docs/PRD-2024-0312.md
acceptance:                    # 必须是可验证的
  - 顶部有状态下拉，选项来自接口
  - 切换状态后列表重新加载
  - 无数据时显示空态插画
  - 分页保留当前状态
needs:
  backend:
    - method: GET
      path: /api/orders
      query: [status, page]
  ui:
    - design: docs/mockups/order-list.png
affected:
  - src/views/OrderList.vue
  - src/api/order.ts
```

**为什么这一步要「停下来问」**：验收标准是后面所有测试的判据。
编一个出来，最后就是「测了个假东西」。

---

## 2. 建分支

| | |
|---|---|
| **输入** | 需求对象 |
| **动作** | 按规则生成分支名 → 从指定 base 切出 |
| **输出** | 新分支 + 记录 base |
| **门禁** | ① 分支名匹配配置里的正则 ② base 存在且已拉取最新 ③ 工作区干净 |
| **失败** | 分支名生成不出来 → 问人；工作区脏 → 先让人处理，不许 stash 掉别人的东西 |

规则在 `workflow.yaml` 里：

```yaml
branch:
  pattern: "feature/{ticket}-{slug}"
  base: test
  slug:
    max_length: 40
    separator: "-"
    lowercase: true
```

---

## 3. 计划

| | |
|---|---|
| **输入** | 需求对象 |
| **动作** | 拆成步骤，**标注依赖** |
| **输出** | 持久化计划（跨会话、跨挂起） |
| **门禁** | 每个验收标准都要有对应步骤覆盖 |
| **失败** | 有验收标准没被覆盖 → 计划不完整，补 |

关键：步骤要能标记「等外部」。这决定了第 5 步。

```yaml
steps:
  - id: s1
    what: 定义接口类型与 mock
    status: done
  - id: s2
    what: 实现状态下拉
    status: done
  - id: s3
    what: 接真实接口，替换 mock
    status: blocked
    blocked_on:
      kind: backend
      checks:
        - GET /api/orders?status= 返回 200 且含 total 字段
      resume_hint: 后端提供后说「继续」
```

---

## 4. 实现（前端优先 + mock）

| | |
|---|---|
| **输入** | 计划 |
| **动作** | 写代码；需要后端的先用 mock |
| **输出** | 改动 + 构建产物 |
| **门禁** | ① 项目能构建（`npm run build` 退出码 0）② 改动不超出计划范围 |
| **失败** | 构建失败 → 自己修，连修 N 次还不行就停下来汇报 |

**mock 必须按项目既有约定**，不能自己发明一套。约定从哪里来：

```yaml
mock:
  strategy: existing_convention     # 跟随项目 | 指定目录 | 指定库
  dir: src/mocks
  detect: ["src/mocks/**", "**/*.mock.ts", "msw"]
```

**为什么要检测而不是写死**：每个项目不一样。写死等于换个项目就失效。

---

## 5. 挂起（等后端）

这是**现在完全没有**的能力。

| | |
|---|---|
| **输入** | 计划里被 blocked 的步骤 |
| **动作** | 记录等待条件 → 会话搁置 |
| **输出** | 可恢复的挂起状态 |
| **门禁** | 挂起必须带**可判定的恢复条件**，不能只说「等后端」 |
| **失败** | 写不出可判定的条件 → 说明依赖没理清，回去问 |

**挂起期间跨会话、跨重启**。三天后你切回来，agent 要能说：

```
这个任务在等 2 个接口：
  GET  /api/orders?status=     上次检查：404
  POST /api/orders/batch       上次检查：404

要现在检查一下吗？
```

**恢复条件必须机器可判定**：

| 好 | 坏 |
|---|---|
| `GET /api/orders 返回 200 且 JSON 含 total` | 「后端好了」 |
| `npm run build 退出码 0` | 「代码写完」 |
| `文件 src/api/order.ts 存在` | 「接口提供了」 |

---

## 6. 联调

| | |
|---|---|
| **输入** | 挂起条件 |
| **动作** | 检测后端 → 对比 mock 与真实 → 切换 → 修差异 |
| **输出** | 用真实接口的代码 |
| **门禁** | 真实响应结构与前端预期一致（字段名、类型、必填性） |
| **失败** | 结构不一致 → 报告差异，**不擅自猜后端意图** |

**这一步的价值在「对比」**：

```
mock 期望：{ items: [], total: 0, page: 1 }
真实返回：{ data: [], pageNo: 1 }

差异：
  ✗ items  → 实际是 data
  ✗ total  → 实际没有这个字段
  ✗ page   → 实际是 pageNo

这批差异该由前端适配还是让后端补字段？请确认。
```

## 7. 自动测试 —— 最大的缺口

拆成四个独立子能力。

### 7.1 把项目跑起来

| | |
|---|---|
| **输入** | 启动命令（来自配置） |
| **动作** | 后台启动 → **等端口就绪** → 拿到地址 |
| **输出** | 运行中的服务 + 日志句柄 |
| **门禁** | 就绪探测通过（不是 sleep 固定秒数） |
| **失败** | 超时 → 读日志，报告真实报错 |

**现在做不到**：`run_bash` 是「跑完才返回」+ 超时杀进程。
起 `npm run dev` 只会挂到超时。

**「等端口就绪」为什么必须是探测而不是 sleep**：
sleep 5 秒在慢机器上不够、在快机器上白等；而且**服务崩了也会继续**。

### 7.2 逻辑测试

| | |
|---|---|
| **输入** | 测试命令 / 内嵌运行时 |
| **动作** | 跑单元测试或直接执行逻辑 |
| **输出** | 通过数 / 失败数 / 失败详情 |
| **门禁** | 失败数 = 0 |
| **失败** | 自己修，修不好停下汇报（不许删测试让它变绿） |

### 7.3 功能测试（操作）

**现在完全没有**——`render_page` 只能渲染截图，不能点、不能输入、不能断言。

需要的原语（**给 agent 用的，不是让它自己写脚本**）：

| 原语 | 说明 |
|---|---|
| `open` | 打开页面，等就绪 |
| `click` | 点元素（按角色/文本/选择器） |
| `type` | 输入 |
| `select` | 下拉选择 |
| `wait_for` | 等条件：元素出现/消失、网络静默、URL 变化 |
| `assert` | 断言：文本、DOM、请求 |
| `snapshot` | 截图（供样式对比） |

**为什么是原语而不是「跑测试框架」**：测试框架要求先写测试文件。
而这里的场景是「按 PRD 的验收标准现场验证」——agent 需要的是**能操作**，
不是**能生成测试代码**（后者也要，但那是另一个层次）。

验收标准 → 操作序列的映射：

```
「切换状态后列表重新加载」
  → click 状态下拉 → select "已完成" → wait_for 网络静默 → assert 列表项状态都是「已完成」
```

### 7.4 样式还原

| | |
|---|---|
| **输入** | 设计稿 + 渲染截图 |
| **动作** | 稳定化 → 像素对比 |
| **输出** | 差异百分比 + 热力图 |
| **门禁** | 差异 < 阈值（可配置，默认 1%） |
| **失败** | 报告差异最大的区域，引导修改 |

**稳定化是准确性的前提**（现在没有）：

| 污染源 | 处理 |
|---|---|
| 时间/日期 | 冻结到固定值 |
| 动画/过渡 | 全局禁用 |
| 随机数据 | 固定种子 |
| 字体渲染差异 | 锁定字体 + 视口 + DPR |
| 接口数据 | 用固定 fixture |
| 滚动位置 | 明确指定 |

**不做稳定化的话** `pixel_diff` 的数字没有意义——同一页面两次截图都能差 5%。

### 7.5 测试门禁（**关键**）

| | |
|---|---|
| **输入** | 7.2 / 7.3 / 7.4 的结果 |
| **动作** | 汇总 → 判定 |
| **输出** | **确定性的** 通过 / 不通过 |
| **门禁** | 全部通过才放行提交 |

**为什么这是关键**：现在 agent 跑完命令，**自己看 stdout 判断过没过**。
模型可能看错、可能乐观。

生产上必须是：**门禁不过，`git_commit` 工具直接拒绝执行**。
不是靠提示词说「请确保测试通过」——那是祈祷，不是门禁。

```
$ agent 想提交
✗ 被拒绝：测试门禁未通过

  逻辑测试    ✓ 42/42
  功能测试    ✗ 5/6   失败：空态插画未显示
  样式还原    ✓ 0.3%
```

## 8. 提交

| | |
|---|---|
| **输入** | 改动 + 需求对象 |
| **动作** | 生成 message（按规范）→ 校验 → 提交 |
| **输出** | commit |
| **门禁** | ① 测试门禁通过 ② message 匹配正则 ③ 改动只涉及计划范围 |
| **失败** | 格式不合 → 重新生成（不许提交后再改） |

```yaml
commit:
  pattern: "^(feat|fix|refactor|test|docs|chore)(\\([a-z-]+\\))?: .{4,72}$"
  require_ticket: true
  template: "{type}({scope}): {subject} (#{ticket})"
  forbid: ["WIP", "fix bug", "update"]
```

**pre-commit hook 失败怎么办**：报告 hook 的输出，**不许 `--no-verify` 绕过**。

---

## 9. 提测

| | |
|---|---|
| **输入** | commit |
| **动作** | 推送 → 等 CI（如果配了）→ 通知 |
| **输出** | 提测完成 |
| **门禁** | ① 目标分支正确 ② CI 绿（如果配了） |
| **失败** | CI 红 → 报告日志，回到第 7 步 |

```yaml
submit:
  target_branch: test
  push_mode: direct          # direct | merge_request
  wait_for_ci: true
  ci_timeout_minutes: 20
  notify:
    kind: webhook            # 可选
    url_env: VA_TEST_NOTIFY_URL
```

## 10. 反馈闭环（工作流自进化）

| | |
|---|---|
| **输入** | 你的反馈（「mock 应该放 xxx」「commit 要带 scope」） |
| **动作** | 把反馈**变成工作流定义的修改**，给你 review |
| **输出** | 新版本 workflow.yaml |
| **门禁** | 修改必须**可 diff、可回滚**；生效前要你确认 |
| **失败** | 反馈无法转成配置（是模糊的偏好）→ 存进记忆，不入流程 |

**前提：流程必须先是「数据」。** 现在流程散在系统提示词的散文里——
agent 改不了，你也没法 review。

改完之后：

```
我改了 workflow.yaml：

  mock:
  - strategy: existing_convention
  + strategy: fixed
  + dir: src/__mocks__

  原因：你说 mocks 目录约定和实际不符（实际是 src/__mocks__）

  确认后下次生效。[y/N]
```

**版本化**：`workflow.yaml` 进 git，改动有历史、能回滚。

# 第四部分：开发阶段

每个阶段结束都**可用、可验证、能停下**。

---

## 阶段 A：工作流定义成数据（P1，地基）

**为什么先做**：第 10 步（自进化）的前提，也是 2 / 4 / 8 / 9 步的配置来源。
不做这个，那些规则只能硬编码在提示词里，改不了、review 不了。

### 交付物

```
<项目>/.vibe/workflow.yaml      项目级（进 git）
<数据根>/workflow.yaml          用户级默认（跨项目）
```

```yaml
version: 1
branch: {...}
commit: {...}
mock: {...}
test:
  start: "npm run dev"
  ready:
    kind: port
    port: 5173
  logic: "npm run test:unit"
  e2e:
    base_url: "http://localhost:5173"
    cases: []              # 由 PRD 的验收标准生成
  visual:
    threshold: 0.01
    designs: docs/mockups
submit: {...}
```

### 功能

1. **加载**：项目级覆盖用户级，合并成有效配置
2. **校验**：格式、正则、路径是否存在
3. **展示**：界面上能看到当前生效的配置和它的来源
4. **修改**：agent 能提议修改，**改动以 diff 形式让你确认**

### 验收标准

- [ ] 改 `workflow.yaml` 的分支规则 → 建出来的分支名跟着变
- [ ] 配置有语法错 → 启动时明确报错，并指出第几行
- [ ] 项目级和用户级同时存在 → 合并结果可见，能看出每条来自哪
- [ ] agent 提议改配置 → 给出 diff，拒绝后不生效

## 阶段 B：后台任务（P0）

**为什么是 P0**：跑不起项目，7.3 / 7.4 全是空谈。

### 交付物

一组后台任务工具：

| 工具 | 说明 |
|---|---|
| `start_process` | 启动一个长驻进程，返回句柄 |
| `read_output` | 读它到目前为止的输出（增量） |
| `wait_for_port` | 等到端口可连接，或超时 |
| `stop_process` | 停止（含子进程组） |
| `list_processes` | 列出在跑的 |

### 关键设计

**句柄要跨工具调用存活** —— 进程属于**会话**，不属于某次调用。

**必须杀进程组** —— `npm run dev` 会派生子进程，杀父进程会留下孤儿占着端口。

**就绪探测**：

```
不是：sleep 5
而是：每 200ms 尝试连接端口，最多 60 秒；中途进程退出就立刻失败并返回日志
```

**并发上限** —— 每个会话最多 N 个后台进程，防止把机器跑满。

### 验收标准

- [ ] `start_process("npm run dev")` + `wait_for_port(5173)` 能拿到可用地址
- [ ] 服务启动失败（配置错）→ 立刻返回，**带真实日志**，不是等超时
- [ ] `stop_process` 之后端口真的释放（`lsof` 验证）
- [ ] 会话结束/agent 退出 → 所有后台进程被清理
- [ ] 同时起 3 个服务能分别管理

## 阶段 C：E2E 操作原语（P0）——**已完成**

### 实际形态

**一个工具收一串动作**（`browser_run`），而不是七个工具各干一件事。

一次动作一个工具调用 = 一次模型往返。十步的登录流程就是十次往返——
慢，而且每一步都要重新把上下文发给模型。收动作数组则是一次启动、
一次往返跑完。

支持：`goto` / `click` / `type` / `select` / `press` / `wait` / `wait_idle`
/ `assert` / `snapshot`。

定位：`role`（推荐，配 `name`）/ `text` / `label` / `placeholder` /
`testid` / `title` / `css`。

**失败即抛错**，完整报告在错误信息里。理由：① 语义上「测试失败」就是失败，
当成功返回会让模型以为通过了 ② 后面的门禁要能**机器判定**，
靠读文本里有没有 ✗ 太脆弱。

### 原始设计（保留作为参考）

| 工具 | 参数要点 |
|---|---|
| `browser_open` | url、等就绪条件 |
| `browser_click` | 定位方式（role/text/css/testid）、超时 |
| `browser_type` | 定位、文本、是否清空 |
| `browser_select` | 定位、值 |
| `browser_wait` | 条件：元素状态、网络静默、URL、函数 |
| `browser_assert` | 断言：文本、属性、数量、可见性 |
| `browser_snapshot` | 截图（供 7.4 用） |

**定位优先用 role/text 而不是 CSS** —— 用户视角的属性更稳，
而且和「验收标准是人话」更接近。

### 关键设计

**浏览器实例按会话复用** —— 每次新建太慢。

**失败时自动截图** —— 断言失败要能看到当时的画面，否则 agent 只能猜。

**网络记录** —— 断言能针对请求（「点保存后应该发出 PUT /api/orders/1」）。

### 验收标准

- [ ] 能完成一次完整登录流程（打开→输入→点击→断言跳转）
- [ ] 断言失败时返回：期望值、实际值、截图、页面当时的控制台报错
- [ ] 元素等不到时，报错要说明「等了什么、等了多久、页面当时有什么」
- [ ] 一次会话里连续操作 10 步不泄漏浏览器进程

## 阶段 D：测试门禁（P0）

### 交付物

**不是工具，是机制** —— 测试结果成为提交的前置条件。

```
test_runs（会话内）
  ├─ logic   : {passed: 42, failed: 0, at: ...}
  ├─ e2e     : {passed: 5,  failed: 1, at: ...}
  └─ visual  : {diff: 0.003, at: ...}

gate = 全部通过 && 测试发生在最后一次代码改动之后
```

**「测试发生在最后一次改动之后」很关键** —— 否则会出现
「改完代码 → 拿旧结果过门禁 → 提交了没测过的代码」。

### 关键设计

**门禁在工具层拦，不在提示词里说**：

```
git_commit 被调用
  → 检查 gate
  → 未通过：直接抛错，附上哪项没过、为什么
  → 通过：正常提交
```

**允许显式豁免，但要留痕**：`git_commit(override_gate="原因是…")`，
这条会写进 commit message 和会话记录。**让人能事后发现绕过**。

### 验收标准

- [ ] 测试失败时 `git_commit` 被拒，错误信息说清哪项没过
- [ ] 改完代码不重跑测试 → 门禁失效（要求重跑）
- [ ] 显式豁免能提交，但 commit message 里带标记
- [ ] 没配测试的项目不受影响（门禁默认关闭）

# 第五部分：关键设计决策

这些需要你拍板，会影响后面所有实现。

## D1. 内嵌运行时：V8 还是浏览器？——**已定：用浏览器，不做 V8**

**必须二选一（或都做，但要分开算）。**

| | 纯 V8 | 浏览器 |
|---|---|---|
| 逻辑测试 | ✅ 快 | ⚠️ 慢 |
| DOM / 事件 | ❌ 没有 | ✅ |
| **样式还原** | ❌ **做不到** | ✅ **唯一选择** |
| 外部依赖 | 无 | 需要浏览器二进制 |
| 体积 | 小 | 大（100MB+） |

**你的需求里有「保证样式还原 UI」——这条只有浏览器能满足。**
纯 V8 没有 CSS 引擎、没有布局、没有绘制。

所以问题变成：
- **A. 要「去掉外部浏览器依赖」** → 内嵌 headless 浏览器
- **B. 要「一个快的 JS 沙箱做逻辑测试」** → V8，但样式还原仍需浏览器
- **C. 两个都要** → 工作量翻倍

**已定：用浏览器（外部 Chromium，即现在 `render_page` 那套），不做内嵌 V8。**

理由：样式还原是硬需求，而纯 V8 没有 CSS 引擎、没有布局、没有绘制，
**根本做不到**。内嵌 V8 只能加速逻辑测试，收益不足以支撑额外维护一个运行时。

后续如果逻辑测试成为瓶颈，再单独评估 V8 沙箱。

## D2. 测试门禁的严格程度

| 选项 | 后果 |
|---|---|
| 严格（不过就不许提交） | 安全，但可能卡住你 |
| 宽松（警告但放行） | 灵活，但形同虚设 |
| 严格 + 显式豁免（留痕） | **我推荐** |

## D3. CI 集成方式

- 只推送，不管 CI → 简单，但不知道测没测
- 推送 + 等 CI 结果 → 闭环，但要处理超时/权限
- 推送 + 开 MR → 更规范，但需要平台 API

## D4. 挂起期间的状态存哪

- 会话文件里 → 简单，但换会话就看不见
- 项目里 `.vibe/tasks/` → 可见、可进 git、跨会话，但要处理冲突
- **我推荐项目里** —— 任务状态是项目的事，不是某次对话的事

## D5. 谁的配置优先

用户级 `<数据根>/workflow.yaml` 和项目级 `<项目>/.vibe/workflow.yaml`：
- 项目级覆盖用户级（我推荐）
- 合并时深层对象是**替换**还是**递归合并**？
- **我推荐递归合并**，但列表是替换（列表合并很容易出意外）

# 第六部分：风险清单

| 风险 | 影响 | 对策 |
|---|---|---|
| **样式还原的稳定化做不彻底** | 差异度虚高，门禁永远不过 → 被绕过 | 先拿一个真实项目标定阈值；持续截图差异 < 0.1% 才算合格 |
| **测试门禁太严** | 卡住正常流程，人被逼着绕过 | 提供显式豁免（留痕）+ 按项目配置严格度 |
| **E2E 脆弱** | 元素定位一改就挂，维护成本高 | 优先 role/text 定位；失败自动截图辅助定位 |
| **长驻进程泄漏** | 端口占满、机器变慢 | 杀进程组 + 会话结束统一清理 + 并发上限 |
| **mock 约定识别错** | 代码风格和项目不一致 | 识别不出来时**问人**，别猜 |
| **挂起条件不可判定** | 「等后端」变成永远等下去 | 门禁强制要求可判定的条件 |
| **工作流配置被改坏** | 整个流程跑不动 | 校验 + 进 git（可回滚）+ 生效前确认 |
| **agent 删测试让它变绿** | 门禁形同虚设 | 显式禁止；门禁记录「测试文件是否被改动」 |
| **内嵌浏览器体积/平台适配** | 部署变复杂 | 先支持一个平台；外部 Chrome 作为回退 |
| **多平台 CI 环境不一致** | 本地绿 CI 红 | 门禁以 CI 结果为准（如果配了） |

---

# 第七部分：明确不做的

| 不做 | 为什么 |
|---|---|
| 让 agent 自己写 E2E 测试文件 | 那是另一个层次（测试代码也要维护）。先用操作原语现场验证 |
| 自动修复 CI 失败 | 先做到「报告清楚」，自动修风险太大 |
| 多平台内嵌浏览器 | 先一个平台，外部 Chrome 回退 |
| 自动决定需求优先级 | 那是人的事 |
| 绕过 pre-commit hook | **绝对不做**，宁可失败 |
| 自动合并到主干 | 提测为止，合并要人决定 |

# 建议的实施顺序

```
第一批（能跑通最小闭环）
  A 工作流定义  →  B 后台任务  →  C 操作原语  →  D 测试门禁
  产出：PRD → 代码 → 测试 → 提交，自动跑通（mock/联调先人工）

第二批（补全你流程里的其余环节）
  E 挂起恢复  →  F 约定校验  →  I 工作流自进化

第三批（准确性）
  G 稳定化 + 样式还原  →  H 提测闭环
```

**为什么 A 放最前**：2/4/8/9 都要读它，后做等于返工四次。
**为什么 D 紧跟 C**：没有门禁，「测试通过才提交」就只是句口号。
